## Phase 1 implementation foundation: detailed work package

This is the recommended first coding phase after approval, not authorization to start now.

1. Add `Business` with lifecycle state and create a MERIBA seed path in schema/data migrations only after migration owners approve.
2. Add `BusinessMembership` that references existing `accounts.User`; map existing role names without removing `User.role` in the first release.
3. Add branch access semantics. Decide explicit all-branches vs selected-branches representation before implementing permissions.
4. Define a typed `TenantContext` carrying verified business, selected branch, membership, effective role and allowed branch IDs. Resolve it after DRF authentication.
5. Replace `get_branch()` usage behind a compatibility service that requires verified request context; fail closed when no context is selected. Inventory non-request callers such as management commands and services.
6. Add context/membership API responses and a context switch endpoint, using existing session + CSRF rather than adding browser tokens.
7. Update backend test fixtures to create two businesses, multiple branches, global users with separate memberships, and branch restrictions. Keep a MERIBA compatibility fixture only where relevant.
8. Add an API endpoint inventory test/checklist so newly added routes must declare permission classes and tenant scoping.
9. Do not alter production config, access production DB, run migrations against production, modify business rules, or add subscription billing in the foundation phase.

## Optional commercial scope (separate approval)

Subscription plans, invoicing, billing provider, trial periods, automated tenant suspension, quotas, usage metering, platform support console and customer support access are not required to prove tenant isolation. Implement only after pricing, tax/legal, payment provider, grace period, data export/retention and suspension policies are decided.
